# Reporting: справка по объектам

Здесь описаны данные и методы сервиса. Нужные изменения для ЛР1 перечислены в [TASK.md](TASK.md).
Часть методов уже реализована в заготовке, остальные добавляются по мере выполнения работ.

## Данные и поведение

Reporting строит отчёты по готовым записям операций. Запись отказа сохраняет сумму попытки, но эта сумма не считается расходом.

`TransactionRecord(transaction_id, customer_id, merchant_id, amount: Money, status, timestamp)` — неизменяемая запись с положительной суммой и статусом `APPROVED` или `DECLINED`. `APPROVED` означает завершённую покупку со списанием, не промежуточную авторизацию. Время передаётся явно; проверка UTC уже готова.

| Объект | Правила |
|---|---|
| `ReportRow(key, count, amount, status)` | Готовая неизменяемая строка. `count >= 1`, статус — `APPROVED`, `DECLINED` либо `None` для суммы успешных операций. |
| `Report(title, currency, rows)` | Хранит строки как `tuple`. Суммы всех строк — в валюте отчёта. |
| `approved_total` | Сумма `row.amount` для строк со статусом, отличным от `DECLINED`. Уже агрегированную сумму не нужно умножать на `count`. |

Общий интерфейс — `ReportBuilder.build(records, currency) -> Report`. `TransactionHistoryReportBuilder` сохраняет входной порядок записей выбранной валюты. `DeclinedTransactionsReportBuilder` выбирает отказы той же валюты, сохраняя их относительный порядок.

`ReportingService.build(currency)` передаёт снимок готового хранилища выбранной реализации. Хранилище, отбор по валюте и группировка уже предоставлены. Здесь слово `Builder` обозначает класс построения отчёта, а не отдельное требование реализовать одноимённый паттерн.

## Работа с готовым кодом

Обращение к сервису выполняется через `app/api.py`. Разрешённые файлы указаны в [TASK.md](TASK.md).
Проверки используют подготовленные данные и не зависят от работы других групп.

Функции `create`, `make`, `call` и `view` связывают готовый API с реализацией. Используемые ими функции сервисного модуля должны сохранять сигнатуры. Сам `app/api.py` не редактируйте.

До ЛР5 сборка предоставлена готовой. Нужные объекты могут создаваться в сервисном модуле; `assembly.py` менять не нужно.

Режимы сборки — `history` и `declined`, с ЛР6 также `merchant_summary`. По умолчанию используется `history`; код валюты передаётся в `build()` позиционно.

## Ошибки и результаты

`DomainError` содержит код ошибки. При отказе проверки состояние объекта не должно меняться.
Ошибка переданной зависимости не заменяется успешным результатом. Конкретные коды и примеры
приведены в задании и открытых тестах.
