# ЛР3. История и список отказов

Вариант: **Reporting**.

## Что дано

Предметные объекты, внешний API и вспомогательные типы уже подготовлены. В `app/domain/builders.py` даны заготовки общего интерфейса и двух исполнителей. Их поведение и основной метод `ReportingService.build()` требуется завершить самостоятельно. Сигнатуры сохранены; новые слои и выбор архитектуры не нужны.

## Задание

### Шаг 1. Реализуйте общий интерфейс и два поведения

Реализуйте `ReportBuilder` и два наследника. `TransactionHistoryReportBuilder` создаёт отчёт «История операций» по всем записям выбранной валюты. `DeclinedTransactionsReportBuilder` создаёт «Отклонённые операции» только по `DECLINED`.

В обычной строке `key=transaction_id`, `count=1`, сумма и статус берутся из записи. Оба класса возвращают `Report`, сохраняя относительный порядок выбранных операций.

### Шаг 2. Соберите путь вызова в `ReportingService.build()`

Проверьте код валюты, передайте текущие записи выбранному `builder.build(records, code)`, затем вызовите `validate_report(result, code)`. Не подменяйте результат другим отчётом. Не выбирайте алгоритм по конкретному классу исполнителя.

### Шаг 3. Проверьте повторное использование

Получите отчёт EUR, отклоните повтор ID, добавьте запись USD. Новый USD-отчёт и старый EUR-отчёт сохраняют собственные суммы и строки.

## Примеры и границы

- Для `T1 APPROVED 10`, `T2 DECLINED 20`, `T3 APPROVED 5 EUR` история содержит три строки и итог `15 EUR`.
- Отчёт об отказах содержит одну строку, его расход равен нулю.
- USD не входит в EUR-отчёт; пустая выборка даёт `Report` с пустым `tuple`.

Последовательности и конфигурации дополнительно проверяются в `tests/test_progression.py`. Прочитайте ожидаемый результат каждого сценария до реализации.

Все проверки открыты: `tests/test_contract.py` и `tests/test_review_contract.py`.
Описание объектов — в [REFERENCE.md](REFERENCE.md), исходные результаты тестов — в [STARTER-STATE.md](STARTER-STATE.md).
